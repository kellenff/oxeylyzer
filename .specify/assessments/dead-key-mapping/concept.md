# Concept: Close the Comprehension Gap Around Dead Keys

- **Slug**: dead-key-mapping
- **Created**: 2026-10-12T17:31:54Z
- **Revised**: 2026-10-12T18:02:00Z — recommendation changed from A to B after the user established this repo is a **private fork**, which removes the only objection to deleting the helper. See Option B and Recommendation.
- **Recommended option**: **B — Delete the redundant helper** (carrying A's documentation work with it)

## Options

### Option A — Pin the behavior (document + assert, change no API)

- **Sketch**: The dead-key helper stays exactly where it is and keeps doing what it does. What changes is what a reader can trust. The docstring names which side of the mapping is input, in the same corpus-char → keystroke language the rest of the cleaner already uses. The doctest gains an assertion, so the example pins behavior instead of merely compiling. One focused test states the direction in prose a future reader can't misread. The README's `to_multiple` section — which already describes `*` as "an accent key" for Spanish and French — says the word "dead key" at least once, so a config author searching for it lands on the mechanism that works. Then the four records that currently disagree (`TODO.md`, the queue skip note, `intake.md`, the wiki page) get reconciled to the one framing the triage established. Nothing a user configures changes.
- **Appetite**: **small** (hours to a day). The metric table in `problem.md` is eight rows; this touches six of them, and none of the six require executing new logic — they require writing it down. Every file it touches is text. Uncertainty is low because the target files are few and already identified.
- **Trade-offs**: **Wins**: directly attacks the demonstrated failure mode (a reader misreading the direction), zero risk to shipped configs or scores, no data regeneration, no `DATA_VERSION` movement, no API change, and it is reversible. It also makes the redundancy visible — an honest docstring saying "this is `multiple` with a dead key" is what lets a later reader decide whether the helper earns its place. **Sacrifices**: leaves `with_dead_key` as dead code with zero callers, so the crate ships a `pub` builder method nobody uses; does not give a config author a shorter spelling; and adds documentation debt to maintain. It is also not the feature the idea was pitched as, so anyone expecting a `[dead_key]` section will read this as a non-answer. **Risk**: documentation is the artifact most likely to rot, and the thing that rotted here was generated by a doc-writing pass (`13327a7`, "add docs and doctests using gemini"), which suggests docs in this repo are produced in bulk and not verified — so an assertion is doing more of the work than prose is.
- **Rabbit holes**: (1) The commented-out parameter `// include_uppercase: bool,` at `corpus_cleaner.rs:286` is an open invitation to "finish" the helper while writing about it; that is Option C's scope and must stay out. (2) "Document the direction" can quietly become "document the whole cleaner contract" — shift, repeat, `REPLACEMENT_CHAR`, uppercase generation all have the same ambiguity, and `normalize_misc_punctuation` normalizing `´` → `'` is a genuinely confusing interaction worth a sentence but not a chapter. (3) Record reconciliation can balloon into re-auditing every `TODO.md` entry and every wiki page; scope it to the four named records.

### Option B — Delete the redundant helper

- **Sketch**: Remove `with_dead_key` from the public surface entirely. `multiple` is the only way to express corpus-char → keystroke-sequence mappings, and it already produces byte-identical output — confirmed by execution in S012. The README's `to_multiple` section is updated to name dead keys explicitly, the stale TODO at `corpus_transposition.rs:225` is corrected (shift and repeat are wired), and the records reconcile. The codebase shrinks and the second spelling disappears.
- **Appetite**: **small** (under a day), and now bounded by evidence rather than by an open question.
- **Trade-offs**: **Wins**: eliminates the ambiguity at its root rather than annotating it — there is no longer a helper to misread; removes code with a permanently-zero caller count; answers the wiki's own unanswered question ("whether `with_dead_key` should exist at all") in the affirmative-negative; deletion beats addition; and it is strictly less documentation to maintain than A, because the thing that rotted disappears instead of gaining prose.
  **Sacrifices**: forecloses the ergonomic name for the next author who wants to express a dead key in code rather than TOML. It also means `problem.md`'s "doctest asserting" and "docstring names the input side" metrics cannot be met *by fixing them* — they are met by removing the artifact, so the surviving signals are the README statement, the direction test on `with_mappings`, and record reconciliation. And one shipped-path check is required rather than optional: deleting a `pub` method must leave `cargo test -p oxeylyzer-core` and the REPL build green, which they will only if the grep evidence holds.
  **The objection that previously blocked this option is now resolved**: this repo is a **private fork** (user-established, 2026-10-12), so the published crate is not a downstream of this work. Recorded honestly in one place: `oxeylyzer-core` on crates.io is upstream `o-x-e-y`'s publication, not this fork's, and `origin` is `kellenff/oxeylyzer`. If any part of this ever goes back upstream as a PR, removing a `pub` method from a published crate is still an API change there — that is upstream's decision to make, not a cost of this fork's work.
- **Rabbit holes**: (1) **Deletion-by-attraction.** Once one dead helper goes, the adjacent candidates become visible, and this repo has real traction for "while we're here": `generate.rs:1205` carries an `#[allow(dead_code)]`, and commit `0ba587a` ("add allow(dead_code) to some obsolete functions") looks like a precedent for keeping code — but it is not one, because those files were deleted at the v2 restructure (`6dcc870`, verified below). (2) **`obsolete.rs` is not a deletion candidate** and must not be swept in: its `best_swap`/`score_swap` are live, called from `generate.rs:1343`, `generate.rs:1364` and `benches/generation.rs:35,39,88` as the correctness oracle for the cached path. (3) A near-neighbour surfaces on the same read: `is_raw()` is referenced only by its own two doctests (`:60`, `:99`), i.e. the same dead shape as `with_dead_key`. Out of scope here; note it so the next author doesn't mistake a partial sweep for a complete one.
- **Evidence gathered at revision** (replaces the unchecked reverse-dependency assumption):
  - `git grep "with_dead_key"` across the working tree and all history-touching refs: the **only** code reference is its own definition (`corpus_cleaner.rs:282`) and its own doctest (`:279`). Every other hit is prose — `TODO.md`, `wiki/`, `.specify/bugs/`, `.specify/assessments/`.
  - Caller counts for every builder method, so `with_dead_key`'s `refs=1` is read in context: `with_chars` 5, `with_mappings` 3, `with_char_mappings` 3, `with_exact_mappings` 3, `with_uppercase_mappings` 4, `qwerty_punctuation_mappings` 4, `normalize_misc_punctuation` 2, `shift_char` 2, `repeat_key` 5, `build` 17, `raw` 9 — **all ≥ 2, most reached from the REPL's `From<CorpusConfig>` path.** `with_dead_key` at 1 (self-referential doctest only) is the sole outlier in the API.
  - `0ba587a`'s annotated files `src/translation.rs` and `src/load_text.rs` were **deleted** at `6dcc870` "prepare oxeylyzer monorepo" — they do not exist in the tree. The apparent keep-and-annotate precedent is a 2022-v1 artifact; the actual outcome was deletion. This removes the main counter-argument to B.
  - `obsolete.rs` confirmed live-as-test-oracle; `CLAUDE.md:95` states it "holds the non-cached `best_swap`/`score_swap` used by tests to validate the cached path," and the call sites confirm it.

### Option C — Add a `[dead_key]` config surface

- **Sketch**: The originally-intended feature. `CorpusConfig` gains a dead-key section, wired through `From<CorpusConfig> for CorpusCleaner`, clearing the TODO at `corpus_transposition.rs:225`. A config author declares a dead-key character and the composed letters it produces, instead of hand-writing `["á","´a"]` pairs. This is the only option that delivers something a config author could newly do.
- **Appetite**: **medium** (days to a couple of weeks) — and the evidence for *small* here is thin. Cost is dominated not by the mapping code, which is a dozen lines, but by the surface around it: TOML shape, inheritance merge semantics in `Add for CorpusConfig`, interaction with `uppercase_versions`, and documentation. No user signal bounds it, so this appetite is a floor, not a forecast.
- **Trade-offs**: **Wins**: the stated idea; a shorter spelling for a common config pattern; makes the TODO at `:225` truthful. **Sacrifices**: it adds a **second mechanism for something one already does**. `with_dead_key` produces output identical to `with_mappings`, and `with_mappings` is reachable from `[multiple]` today — so this option's user-visible gain over `["á","*a"]` is typing. It creates a consistency obligation: two config fields expressing the same mapping will diverge. Research found **zero demand** — no issue, no config field in any of 51 shipped configs, and the one relevant external user (issue #34) is *commenting dead keys out* of their keylogger to avoid the problem. **Risk**: any temptation to make the new field "just work" by editing `default.toml` cascades into invalidating all shipped `language_data/*.json` and every existing layout score, gated by a hand-bumped `DATA_VERSION` sentinel.
- **Rabbit holes**: (1) **The `´` collision is the real one.** `default.toml`'s `[one_to_one]` already normalizes `´` → `'` (and `normalize_misc_punctuation` does the same in core). A dead key spelled with the accent character is eaten by inherited defaults before the mapping sees it, so making the intuitive spelling work requires changing normalization — which is a data-version event, not a feature. (2) Answering "does a dead key generate an uppercase form?" by *not* reusing `uppercase_versions` duplicates logic that already works correctly. (3) "While the config surface is open, expose it in the GUI too" — unexamined; no Tauri source was read at any stage of this pipeline. (4) True two-character *input* sequences (`´a` in a corpus collapsing to `á`) are a different feature and would need the `SlidingWindow` path, which today is allocated only when `repeat_key` is enabled.

## Recommendation

**Option B — Delete the redundant helper, carrying A's documentation and reconciliation work with it.**

The revision is driven by one new fact from the user: this is a private fork. That removes the single objection I recorded against B, and once it is removed, B is both the better answer to the problem and the smaller change. `problem.md` defines the defect as comprehension — a reader could not tell that `multiple` is the dead-key mechanism, and `with_dead_key` was the artifact that invited the misreading. Deleting the inviting artifact is a more direct fix than writing prose to disambiguate it, and it is also strictly less to maintain.

Three pieces of evidence, gathered at revision rather than assumed, are what make this recommendable rather than merely permissible:

1. **The helper is genuinely unreachable.** `with_dead_key` has exactly one reference in the whole tree — its own doctest. Against a builder API where every other method is reached at least twice and most from the REPL's `From<CorpusConfig>` path, it is the lone orphan. Zero callers since it was added in `0541468`.
2. **The repo's precedent is deletion, not annotation.** I had noted `0ba587a` "add allow(dead_code) to some obsolete functions" as the house convention arguing for keeping code. Checking it: those files were deleted at `6dcc870` "prepare oxeylyzer monorepo." The annotation was temporary and the code is gone. That was the strongest counter-argument to B and it does not survive verification.
3. **`obsolete.rs` is a false candidate and stays.** Its functions are the live correctness oracle for the cached scoring path (`generate.rs:1343,1364`, `benches/generation.rs`). Naming this explicitly is what keeps B from becoming a sweep.

The honest cost: two of `problem.md`'s eight metrics are satisfied by *removal* instead of *repair* — there is no longer a docstring or doctest at `corpus_cleaner.rs:272-293` to fix. The remaining signals still hold and still need doing: a direction test on the surviving `with_mappings` path, the README naming dead keys next to "accent key" at `:177`, correcting the stale shift/repeat claims at `corpus_transposition.rs:225`, and reconciling the four disagreeing records (1 of 4 → 4 of 4). A is therefore not a rejected option so much as a **subset of B** — its documentation scope is inherited, minus the helper's own prose.

**C remains not recommended**, for the reason it was originally rejected and unchanged by the new fact: its premise — that dead-key mapping is missing — was tested and did not hold, it adds a second spelling of a mechanism that already produces identical output, it has zero demand signal across 51 shipped configs and one adjacent issue, and the `´` → `'` normalization collision is demonstrated capacity to blow past its appetite into a data-version event.

**One residual, stated for `decide` rather than buried**: the upstream crate is still published at `0.1.x`/`0.2.0` by `o-x-e-y`. Fork-local work has no downstream. If anything here is ever offered back upstream, the deletion is an API change on *their* terms and their decision — which argues for keeping the deletion in a separable commit from the documentation work.

## Out of Scope (for the recommended option)

Inherited from `problem.md`, restated, plus additions:

- No new `CorpusConfig` field, including no `[dead_key]` section.
- No true OS dead-key state machine; no two-character input sequence matching.
- No change to `default.toml`, to any of the 51 shipped corpus configs, or to `one_to_one`'s `´` → `'` normalization. That collision is recorded as a constraint on any future design.
- No regeneration of `language_data/*.json`; no `DATA_VERSION` bump.
- No re-litigating the `with-dead-key-inverted` `invalid` verdict.
- No GUI/Tauri work — unexamined at every stage of this pipeline.
- **The commented-out `include_uppercase` parameter** goes away with the helper; reviving it is out of scope.
- **No dead-code sweep.** `with_dead_key` is the only deletion. Specifically out: `generate/obsolete.rs` (live test oracle — `generate.rs:1343,1364`, `benches/generation.rs:35,39,88`), `generate.rs:1205`'s `#[allow(dead_code)]`, and `is_raw()` (its own two doctests at `corpus_cleaner.rs:60,99` are the same dead shape, deliberately left alone so this stays one deletion).
- **No upstream coordination work.** No PR, no issue, no version bump on the published crate. The deletion is fork-local; the separable-commit note in the Recommendation is the whole handling of the upstream question.
- No documentation campaign beyond the named files (`corpus_cleaner.rs` — deletion, `README.md:177` `to_multiple` section, `corpus_transposition.rs:225` TODO) and the four records named in the metric. The broader cleaner contract stays as-documented.

## Assumptions — Validate

1. **No in-repo caller exists.** Verified at revision by `git grep` over the working tree and refs: one self-referential doctest, nothing else. Must be re-verified by build (`cargo test -p oxeylyzer-core`, plus the REPL, which is where a caller would live) during specification, but this is now evidence rather than assumption.
2. **This fork has no downstream consumers of `oxeylyzer-core`.** Supplied by the user as fact, not verified by me — I did not check `origin`'s visibility settings or fork status beyond confirming the remote URL is `kellenff/oxeylyzer`. The recommendation rests on it, so if the fork is later made public or the deletion is offered upstream, revisit.
3. **`cargo test` catches a bad deletion.** Trivially true for a `pub` method with one reference, since removal is a compile error, not a silent behavioral change — this is the least risky property of B. Doctests running in CI remains unverified (no CI configuration was read).
4. **The maintainer wants the *simulated alternation* model that `*` already implements, rather than a true state machine.** Still unresolved — Open Question 1, and still the hinge. If the answer is "true state machine," this problem definition and all three options are the wrong frame and a new intake is needed. Note this one cuts *differently* for B than for A: deleting the helper is the wrong move if a real dead-key feature is planned, because the ergonomic name would then be wanted after all.
5. **Documentation-only and deletion changes need no data regeneration or version bump.** Sound: `language_data/*.json` is produced by cleaning corpora, not by reading docstrings or builder method names, and nothing on the shipped cleaning path changes.
6. **Reconciling four stale records is wanted work, not bookkeeping noise.** Unvalidated — a process preference. It is now the part of the recommendation most likely to be called unnecessary, since after deletion there is no live artifact left to misread and the records are the only remaining trace.
